# Native discovery before dungeon entry

This opt-in helper protocol is for the isolated, single-player, one-living-hero HollowMire setup at FloodedCrypt. It is a controlled repeatability experiment. A quiet introductory story does not prove that moving to a quest destination or entering a dungeon cannot trigger another story. The preserved Reefstrider trial demonstrates that boundary. No new story submission is allowed inside the dungeon.

**Compatibility:** `run_case.py` new-run/resume now requires a helper implementing the three operations below. Earlier helper binaries, including frozen `0c65` and `24c9596a`, do not implement them. Do not launch the updated flow with an old helper. Deployment and fresh live trials remain operator-controlled.

Each command includes the existing `id`, `session`, and `op` envelope. The helper allows only one preparation ticket per session, never removes its claim after an exception, and never starts or restarts a campaign.

1. `entry-preparation-state` accepts optional `ticketId`. It is read-only and returns exact integer `heroInstanceId`, `dungeonInstanceId`, `hexInstanceId`, `movementInstanceId`, and `gameDefinitionIdentity`; `positionEligible`, `discoveryEligible`, `eligibilityReason`; full nested `story` (including fresh native frame, session, root and Core identity); and a nullable `ticket` object. Its first observation pins Core identity for subsequent operations.
2. `entry-position` accepts exactly those five integers. It requires quiescent native story/movement/quest-check state and creates its permanent ticket before **one** `cow.SnapTo(targetHex, false, true)`. Success reports `status: native-position-submitted`, `ticketId` (the command ID), and `before`. It does not claim placement or story completion. Poll state and use the existing exact story-page protocol as necessary.
3. `entry-discover` accepts `ticketId`. It rechecks scope, target hex, movement, existing quest continuations and full quiet story, claims discovery before allocation/invocation, registers one local Self/count1 `ContinueFSM`, and calls **one** native `cow.CheckDiscoverHex`. Success reports `status: native-discovery-submitted`, `ticketId`, `before`, `continuation`, and `callbackCount`. A synchronous callback is valid; success does not imply the asynchronous work is complete.

Ticket fields include `phase`, `valid`, `discoverSubmitted`, `callbackCount`, `callbackFrame`, `callbackRealtime`, `continuation` (`id`, `callerId`, `waitCount`, `waitClients`, `local`), `sameStoredCheckContinuation`, `ownContinuationStillRegistered`, `quietSinceRealtime`, `quietStartFrame`, `entryReady`, and `waitingReason`. Phases use exact strings `position-intent`, `position-submitted`, `position-uncertain`, `discover-intent`, `discover-submitted`, `discover-uncertain`, `invalid-pins-or-scope`, and `invalid-double-callback`. An uncertain action ends the sequence; never retry it or infer that it did not occur.

`entryReady` requires the one callback, consumed own continuation still matching GameEventManager's stored check, native quest-check FSM disabled, other stored check continuations absent or consumed, no moving/sync-walking/waiting, permitted Movement state, no active nested/turn quest check, same current hero/target and outside-dungeon/combat scope. It additionally requires the registered current quest object to reference the existing `ftkmf_hollowmire_crypt` `DungeonQuestDef`, target `FloodedCrypt`, and have its actual destination equal the target hex ID. A runtime quest integer or oneline string is not a substitute. These conditions and full native story completion must remain observed over at least two seconds and fresh Unity frames.

Once freshly ready, the Python caller performs existing `enter_dungeon` followed immediately by stage, preserving their adjacency. The helper never calls entry, OnLoadParty, a raw FSM event, quest completion/flags, or a continuation manually. Post-stage pending Story remains a stopped result, including before combatants exist. Two fresh successful setup trials are required before claiming repeatability.

The callback captures only a bounded managed ticket and stamps its completion metadata. It does not hold avatars, invoke gameplay, or enter reentrantly. Native local continuation completion can leave a consumed manager entry; readout reports that fact and never unregisters arbitrary native continuations. Destroying the helper invalidates its ticket. This is not a claim of native manager entry disposal.

`entry-preparation-tests` links the actual pure policy/progress code and shipped Newtonsoft. It tests refusal and once-only sequencing, including synchronous/asynchronous and invalidated callbacks. It does not simulate native quest FSM execution or establish the live startup gate.
